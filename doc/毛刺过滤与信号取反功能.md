## 4. SigSession::set_glitch_filter() 和 clear_glitch_filter() 的工作方式

**`set_glitch_filter`**（sigsession.cpp 第 2474-2501 行）：
1. 如果已在运行或无逻辑数据，直接返回
2. 检查 thresholds 中是否有非零值，没有则返回
3. 设置 `_glitch_filter_running = true`，发送 `DSV_MSG_GLITCH_FILTER_STARTED` 消息
4. 在独立线程中执行 `glitch_filter_task`

**`glitch_filter_task`**（第 2503-2530 行）：
1. **备份原始数据**：如果 `_logic_backup` 为空，创建新的 `LogicSnapshot` 并 `copy_from` 当前数据；如果已有备份，从备份恢复数据（支持反复调整阈值）
2. 调用 `LogicSnapshot::apply_glitch_filter_all(thresholds, progress_callback)` 对所有通道执行毛刺过滤
3. 设置 `_glitch_filter_active = true`，保存阈值
4. 发送 `DSV_MSG_GLITCH_FILTER_COMPLETED` 和 `data_updated`

**`clear_glitch_filter`**（第 2532-2549 行）：
1. 如果正在运行或未激活，直接返回
2. **从备份恢复原始数据**：`get_logic()->copy_from(*_logic_backup)`，然后删除备份
3. 清除 `_glitch_filter_active` 和阈值
4. 发送 `DSV_MSG_GLITCH_FILTER_CLEARED` 和 `data_updated`

**`apply_glitch_filter`** 的核心算法（logicsnapshot.cpp 第 1939 行起）：
- 状态机扫描：维护一个 `accepted_level`（已确认的稳定电平）
- 遍历所有采样点，检测电平变化
- 如果某段电平持续时间 < threshold，视为毛刺，记录到 `fills` 批处理列表
- 批量应用覆盖并重构 Mipmap 树

**关键设计**：备份机制使得毛刺过滤是**可逆的**——每次 `set_glitch_filter` 都从原始备份数据重新计算，`clear_glitch_filter` 则恢复原始数据。

## 7. SessionDocument 的信号处理管线/数据变换支持

`SessionDocument`（`c:\Users\admin\Downloads\DSView-main_2026_4_27cppnb\PXView\pv\data\sessiondocument.h`）是数据存储层，**本身不包含信号处理管线**。它的职责是：

- **数据存储**：持有 `_logic`（LogicSnapshot）、`_analog`（AnalogSnapshot）、`_dso`（DsoSnapshot）三个快照对象
- **解码器管理**：持有 `_decoder_stacks` 和 `_decode_traces`
- **信号列表**：持有 `_signals`（view::Signal*）
- **频谱/数学**：持有 `_spectrum_traces`
- **配置持久化**：`SignalConfig` 的 JSON 序列化/反序列化，通道配置的保存/恢复
- **Dock 状态**：保存各 dock 面板的会话数据（`_dock_trigger_session`、`_dock_device_options_session` 等）

**信号处理在更高层完成**：
- 毛刺过滤：在 `SigSession` 中管理，通过 `_view_data->_logic_backup` 备份原始数据，直接修改 `LogicSnapshot` 的数据
- 协议解码：通过 `DecoderStack` 在独立线程中运行
- 数学运算：通过 `MathStack` 处理 DSO 数据
- 频谱分析：通过 `SpectrumStack` 做 FFT

`SessionDocument` 的 `copy_from_logic/analog/dso` 方法提供了深拷贝能力，这是毛刺过滤备份机制的基础。但目前**没有通用的数据变换管线接口**——每种变换（如毛刺过滤）都是独立实现的，没有统一的"变换栈"或"变换链"概念。

## 四、内容被压缩/截断的具体机制

### 4.1 QScrollArea + widgetResizable=true 的行为

当 `widgetResizable=true` 时，QScrollArea 会尝试将内部 widget 调整为 viewport 大小。但 Qt 会尊重 widget 的 `minimumSizeHint()`。当 `minimumSizeHint().width() > viewport.width()` 时：

1. widget 实际宽度 = `minimumSizeHint().width()` = 499px
2. viewport 可见宽度 = 350px (或333px)
3. 超出部分 (149-166px) 被 viewport 裁剪，不可见

### 4.2 水平滚动条被强制关闭

```cpp
sp_scroll->setHorizontalScrollBarPolicy(Qt::ScrollBarAlwaysOff);
```

这是关键问题。即使内容溢出，用户也无法通过水平滚动查看被裁剪的内容。内容直接消失在 viewport 右边界之外。

### 4.3 QGridLayout 在父容器宽度不足时的行为

QGridLayout 的布局协商过程：

1. **minimumSize()** 计算：所有列的最小宽度之和 + 间距 + margins = 465px
2. 当父布局分配的宽度 < minimumSize() 时：
   - QGridLayout **不会**压缩 `setFixedWidth(55)` 的控件（fixedWidth 是硬约束）
   - 布局会按照 minimumSize 返回尺寸
   - 父 widget 的 geometry 可能小于布局请求的尺寸
   - 超出父 widget 右边界的子控件被父 widget 的裁剪区域切断

3. 由于所有列的 `setColumnStretch(c, 0)`，没有列会弹性伸缩来适应可用空间

### 4.4 QCheckBox setFixedWidth(55) 的不可压缩性

`setFixedWidth(55)` 等价于同时设置 `setMinimumWidth(55)` 和 `setMaximumWidth(55)`。这意味着：
- 布局系统**绝对不能**将此控件压缩到55px以下
- 8个这样的控件在QGridLayout中形成了465px的硬性最小宽度约束
- 这个约束无法通过任何布局策略绕过

## 六、SmoothScrollArea 对尺寸的影响

### 6.1 继承自 QScrollArea 的尺寸协商

SmoothScrollArea 继承自 QScrollArea，其核心尺寸行为完全由 QScrollArea 决定：

- `widgetResizable=true`：viewport 尝试将 widget 调整为 viewport 大小
- 但 widget 的 `minimumSizeHint()` 优先级更高
- 当 `minimumSizeHint > viewport` 时，widget 保持其最小尺寸，超出部分被裁剪

### 6.2 SmoothScrollArea 的额外影响

SmoothScrollArea 重写了 `wheelEvent`，添加了平滑滚动动画。在动画期间：

```cpp
if (widget() && widget()->layout())
    widget()->layout()->setEnabled(false);  // 动画期间禁用布局
```

动画结束后：

```cpp
widget()->layout()->setEnabled(true);
widget()->layout()->activate();  // 重新激活布局
```

这意味着在滚动动画期间，布局被临时冻结，不会触发重新布局计算。这对宽度溢出问题没有直接影响，但说明滚动动画只处理垂直方向。

### 6.3 垂直滚动条对水平空间的侵占

`sp_container->setMinimumHeight(1000)` 确保内容高度大于典型 viewport 高度，因此垂直滚动条几乎总是可见。垂直滚动条占用约17px宽度，使 viewport 有效宽度从350px减少到约333px，进一步加剧了水平溢出问题。

## 九、根本原因总结

Ch13 文字被裁剪的根本原因是**三层约束的叠加冲突**：

1. **QCheckBox setFixedWidth(55)** -- 硬性约束，8列不可压缩，总最小宽度465px
2. **SlidingDrawer 默认宽度350px** -- 远小于465px的内容需求
3. **SmoothScrollArea 水平滚动条强制关闭** -- `Qt::ScrollBarAlwaysOff`，即使溢出也无法滚动查看

这三者共同导致：当内容最小宽度(499px)远大于可用宽度(333-350px)时，超出部分被viewport直接裁剪，用户既看不到也无法操作被裁剪的控件。`_invert_group->setMinimumWidth(230)` 这个约束(230px)远低于实际布局需求(475px)，形同虚设，没有起到保护作用。
