### 核心原因：`update_visible_items` 中的 `setVisible`

在你的代码中，一旦发生滚动，触发了 `update_visible_items`，你会执行以下操作：
```cpp
// 遍历所有的容器
for (QWidget *container : _glitch_row_containers) {
    // ... 计算相交 ...
    bool isVisible = expandedRect.intersects(containerGlobalRect);
    // ...
    if (contentWidget && contentWidget->isVisible() != isVisible) {
        contentWidget->setVisible(isVisible); // 卡顿的元凶！！！
    }
}
```

**为什么这会极其卡顿？**
1. **触发疯狂的 Layout 重算**：虽然你给外层的 `row_container` 设置了 `setFixedHeight(28)`，但调用内部 `contentWidget` 的 `setVisible` 依然会触发 Qt 的 `Hide/Show` 事件，并向上传递布局失效（Layout Invalidation）信号。
2. **打断了平滑滚动（Smooth Scrolling）**：每次显示/隐藏控件，Qt 都需要重新构建渲染树和事件分发树。如果在滚动过程中（每秒 60 帧）不断进行控件级别的隐藏和显示，CPU 开销远大于直接绘制它们。
3. **坐标转换的开销**：在滚动循环中频繁调用 `mapToGlobal` 也是相对耗时的操作。
4. **日志证实**：你的日志中只有 16 个通道（`total=16`），对于 Qt 来说，同时存在 16 个甚至 100 个简单的 QWidget 根本毫无压力。反而是你为了这 16 个控件去做复杂的可见性计算和状态切换，把 CPU 跑满了。

### 解决方案

#### 第一步：最快见效的修复（强烈建议）
**直接废弃手动视口剔除逻辑。** Qt 的 `QScrollArea` 底层本来就带有极其高效的剪裁（Clipping）机制，**它根本不会去绘制视口之外的控件**。

将 `update_visible_items` 里的内容清空，或者直接注释掉 `setVisible` 的逻辑：

```cpp
void DeviceOptionsDock::update_visible_items() {
    // 方案 A：直接 return，完全信任 Qt 的原生渲染剪裁机制
    return; 
    
    /* 
    // 方案 B：只保留日志，或者彻底删除这个函数
    if (_glitch_row_containers.isEmpty()) return;
    // ... 
    */
}
```
*修改后你会发现滚动瞬间变得丝滑，因为所有的控件都在内存中，Qt 滚动时只是做了简单的像素位移和局部重绘。*

#### 第二步：针对大量数据的终极方案（如果不止 16 个，而是成百上千个通道）
如果你未来的需求里通道数非常多（例如 500 个以上），创建大量的 QWidget（`QCheckBox`, `QSpinBox`, `QLabel`）确实会占用较多内存和初始化时间。但这**不应该通过嵌套 QWidget + 手动 setVisible 来解决**。

正确的 Qt 做法是使用 **Model/View 架构**：
* 使用 `QListView` 或 `QTableView`。
* 自定义 `QStyledItemDelegate`，在 `paint()` 函数中直接用 `QPainter` 画出 Checkbox 和文字。
* 在 delegate 中处理鼠标点击事件（实现 Checkbox 勾选和 Spinbox 的数值修改）。
* *这种做法即使有 10 万行数据，也依然如丝般顺滑，因为 Qt 底层只会实例化屏幕可见区域的那几个 delegate。*

#### 第三步：清理其他潜在的性能隐患
代码中还有几处容易引起偶发卡顿的地方：

1. **`try_resize_scroll` 中的 `findChildren`：**
   ```cpp
   auto labels = _dynamic_panel->findChildren<QLabel *>();
   ```
   `findChildren` 是一个递归遍历整棵控件树的操作，比较耗时。虽然它不在高频的 paint 事件中，但如果是复杂的动态面板，每次切换模式都调一次会带来几毫秒的卡顿。建议在创建 QLabel 时就把它们存在一个 `std::vector<QLabel*>` 或 `QList<QLabel*>` 中，直接遍历列表即可。

2. **多余的定时器：**
   ```cpp

   ```
   每 500ms 检查一次硬件状态本身没问题，但在 `mode_check_timeout` 中调用了 `box->parentWidget()->update()`，确保不要引发不必要的全局重绘。
