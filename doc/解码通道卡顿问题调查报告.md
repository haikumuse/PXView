### 二、三层绘制方法详解

`DecodeTrace` 继承自 `Trace`，实现了三层绘制接口：

#### 1. `paint_back()` — 背景层（第132-191行）

绘制两项内容：
- **水平虚线分隔线**：在轨迹中心位置画一条点线
- **解码区域控制标记**：根据 `_decode_start` / `_decode_end` 计算像素坐标，绘制两个蓝色三角形标记（起止位置指示器）
- **行标题（headings）**：在左侧绘制每行的名称和箭头指示

此方法在每帧都会执行，但计算量很小。

#### 2. `paint_mid()` — 中间层（第193-287行）**核心绘制逻辑**

这是最关键的方法，执行全部注解的渲染。流程如下：

1. **计算可见样本范围**：
   ```cpp
   const double samples_per_pixel = samplerate * scale;
   uint64_t start_sample = (left + pixels_offset) * samples_per_pixel;
   uint64_t end_sample = (right + pixels_offset) * samples_per_pixel;
   ```
   将视口的像素范围转换为样本索引范围。

2. **遍历解码器栈中的每个解码器**，对每个可见行（`rows_gshow`）：
   - 调用 `_decoder_stack->get_min_annotation(row)` 获取该行最小注解宽度（样本数）
   - 计算最小注解的像素宽度：`min_annWidth = min_annotation / samples_per_pixel`
   - 调用 `_decoder_stack->get_annotation_subset(annotations, row, start_sample, end_sample)` 获取可见范围内的注解子集
   - 逐个调用 `draw_annotation()` 绘制

3. **对不可见的解码器**，调用 `draw_unshown_row()` 绘制 "Unshown" 提示

#### 3. `paint_fore()` — 前景层（第289-298行）

**完全为空**，不执行任何绘制操作。

#### 资源去重机制（AnnotationResTable）

注解文本不直接存储在 `Annotation` 对象中，而是通过 `_resIndex` 索引到 `AnnotationResTable`。该表使用 `std::map<string, int>` 做键值去重，相同的文本内容共享同一个 `AnnotationSourceItem`。这大幅减少了内存占用，尤其是协议解码中大量重复的注解文本（如 "0"/"1"、常见状态名等）。

`AnnotationSourceItem` 包含：
- `src_lines`：原始文本行
- `cvt_lines`：格式转换后的文本行（bin/hex/oct）
- `str_number_hex`：十六进制数值字符串
- `cur_display_format`：当前显示格式（-1 表示未初始化）

#### 注解文本获取（`annotations()` 方法）

当调用 `annotations()` 时，会根据 `DecoderStatus::m_format` 判断是否需要重新格式化数值。如果是数值类型且格式已变化，会重新生成 `cvt_lines`，支持 `{$}` 占位符替换。

### 四、缩放到最小时的渲染行为与优化策略

#### 已实现的优化策略

**1. 视口级二分查找裁剪（RowData::get_annotation_subset）**

这是最基础也最重要的优化。`RowData` 使用 `std::vector<Annotation*>` 存储注解（按 `start_sample` 排序），查询时通过 `std::lower_bound` 二分查找定位起始位置：

```cpp
auto it = std::lower_bound(_annotations.begin(), _annotations.end(), start_sample,
    [](Annotation *a, uint64_t val) {
        return a->end_sample() <= val;
    });
```

这确保只获取视口可见范围内的注解，时间复杂度 O(log N + K)，其中 K 是可见注解数量。

**2. 像素级重叠跳过（last_x 机制）**

`draw_annotation()` 中维护一个 `last_x` 引用变量，实现"完美无缝隙 LOD 防御"（代码注释原文）：

```cpp
// 如果当前标注完全被之前绘制的区域覆盖，则不可见，跳过
if (end <= last_x) {
    return;
}

// 如果是极窄标注（只画一根竖线），且该竖线落在已绘制区域，跳过
if (start + 2.0 > end && (int)start <= (int)last_x) {
    return;
}
```

这是**最关键的缩放优化**。当缩放到最小时，数百万条注解可能映射到同一像素列。此机制将实际绘制调用从数百万次削减到约屏幕像素宽度（~1920次），且不会产生视觉缝隙。

**3. 极窄注解简化绘制（draw_range 中的竖线优化）**

当注解宽度小于2像素时，`draw_range()` 不绘制六边形多边形，而是只画一条竖线：

```cpp
if (start + 2.0 > end) {
    p.setPen(fill);
    p.drawLine(QPointF(start, top), QPointF(start, bottom));
    return;
}
```

**4. 小区域跳过文本渲染**

- `draw_instant()` 中：如果宽度 <= 4 像素，跳过文本绘制
- `draw_range()` 中：如果矩形宽度 <= 4 像素，跳过文本绘制

```cpp
if (w > 4.0) {
    p.setPen(text_color);
    p.drawText(rect, Qt::AlignCenter | Qt::AlignVCenter, text);
}
```

**5. QStaticText 缓存**

`Annotation::get_cached_text()` 使用 `QStaticText` 缓存已布局的文本，避免每帧重复进行文本排版：

```cpp
QStaticText* Annotation::get_cached_text(const QString &text, const QFont &font) const {
    if (_cached_text.text() != text || _cached_font != font) {
        _cached_text.setText(text);
        _cached_text.prepare(QTransform(), font);
        _cached_font = font;
    }
    return &_cached_text;
}
```

**6. 最佳注解文本选择缓存**

`get_cached_best_annotation()` 根据矩形宽度从多个注解格式中选择最合适的一个（能放下且最长的），并缓存结果：

```cpp
for (auto &a : ann_list) {
    const int w = fm.boundingRect(QRect(), 0, a).width();
    if (w <= rect_width && w > best_width) {
        best_annotation = a;
        best_width = w;
    }
}
```

**7. 视口双缓冲与独立解码 pixmap**

`Viewport` 为解码轨迹维护独立的 `_decode_pixmap`，仅在 `_decode_needs_rebuild` 为 true 时重建。这避免了解码数据更新时重绘逻辑信号，也消除了 dock 动画期间的卡顿。

**8. 解码数据更新节流**

`on_new_decode_data()` 中使用 `QElapsedTimer` 限制更新频率为最高 50 FPS：

```cpp
if (is_running && elapsed < 20) {
    return;
}
```

**9. draw_unshown_row 的裁剪优化**

使用 `QFontMetrics` 替代 `p.boundingRect()` 来计算文本宽度，并添加了视口裁剪检查：

```cpp

    return;
```

#### 未实现的优化（潜在性能瓶颈）

**1. 无降采样/LOD机制**

`draw_nodetail()` 方法已定义（显示 "Zoom in for details" 提示），但**从未被调用**。当前代码在任何缩放级别下都尝试绘制所有可见注解，没有"概览模式"。

**2. 无注解合并/聚合**

当缩放到极小时，即使有 `last_x` 跳过机制，`get_annotation_subset()` 仍然会返回所有落在可见范围内的注解指针到 `std::vector` 中。如果可见范围内有数十万条注解，这个 vector 的构建本身就有开销（内存分配 + 指针拷贝）。

**3. 无空间索引结构**

`RowData` 使用扁平的 `std::vector<Annotation*>`，虽然二分查找定位很快，但没有 R-tree/B-tree 等空间索引。对于超大数据集（数百万条注解），可以考虑分层索引。

**4. 注解子集查询使用共享锁**

`get_annotation_subset()` 使用 `std::shared_lock`，虽然读操作不互斥，但在解码线程持续写入时仍可能有锁竞争。

**5. draw_annotation 中的标记绘制开销**

当解码器有绑定通道且注解类型匹配时，`draw_annotation()` 会遍历所有信号查找绑定的逻辑信号并调用 `paint_mark()`，这在缩放到最小时可能产生不必要的开销。

### 七、总结：优化策略汇总

| 策略 | 实现位置 | 效果 |
|------|----------|------|
| **阈值判断合并** | `DrawDecode()` 第258行 `len < threshold` | 小于4像素的注解合并为色块，避免绘制不可分辨的细节 |
| **跳跃式遍历** | `DrawDecode()` 第274-281行 | 合并块结束后二分查找跳到下一个可见注解，跳过中间所有注解 |
| **两级二分查找** | `findDecodeRowDataNode()` + `findDecodeRowFirstData()` | 先在稀疏索引中粗定位，再精确查找，O(log N) 复杂度 |
| **稀疏索引节点** | 每10万条数据一个 `DecodeRowDataNode` | 避免在百万级注解中线性扫描 |

| **文本降级渲染** | `DrawDecodeText()` | longText -> text -> 截断+省略号 -> 回退为合并块 |
| **tog/value 压缩跳转** | `Segment::GetDataEnd()` | 逻辑信号渲染时跳过整块相同电平的数据 |
| **引用计数保护** | `appendCite()/lessenCite()` | 渲染期间防止数据被释放，保证线程安全 |
| **互斥锁细粒度控制** | `decode->m_rowList[key]->mutex.lock()/unlock()` | 每次只锁住当前访问的行数据，减少锁竞争 |

### 八、不足与潜在改进点

1. **没有真正的降采样(Downsampling)**：当前策略是"合并过小注解为色块"，但并没有对注解数据进行预聚合或 LOD(Level of Detail) 缓存。每次缩放都需要重新遍历和判断。
2. **没有离屏渲染缓存**：类名叫 `DoubleBuffering` 但实际并没有实现双缓冲——`refReshBuffer()` 直接在传入的 painter 上绘制，没有使用 `QPixmap` 后备缓冲区。
3. **逐条加锁开销**：在 `DrawDecode()` 的主循环中，每读取一条 `DecodeRowData` 都要加锁/解锁一次 mutex，在数据量大时可能产生性能瓶颈。
4. **颜色计算在渲染线程**：`colorState` 的计算（统计前10条数据的类型频率）在渲染循环中执行，应该预计算。

# 解码通道缩放卡顿对比调查报告

## 结论

PXView 缩到最小卡顿的**根本原因**是：在极度缩放时，虽然 `last_x` 跳过了绘制，但仍然**逐条遍历**了可见范围内所有注解，且需要先将全部注解指针**拷贝到临时 vector**。atk-logic-master 则通过**阈值合并 + 跳跃式二分查找**直接跳过不可分辨的注解，避免了遍历开销。

---

## 关键差异对比

| 维度 | atk-logic-master | PXView | 影响 |
|------|------------------|--------|------|
| **过小注解处理** | 阈值合并：`< 4px` 的注解合并为一个色块 | 逐条绘制竖线，仅靠 `last_x` 跳过重复像素 | **核心差异** |
| **数据遍历方式** | 合并块结束后二分查找跳到下一可见注解 | 线性遍历 `annotations` vector 中的每一条 | 百万注解时差距巨大 |
| **子集查询** | 直接用索引访问，无临时容器 | `get_annotation_subset()` 将所有可见注解指针拷贝到临时 `vector<Annotation*>` | 大量内存分配+拷贝 |
| **概览模式** | 合并块 + 斜线纹理，视觉区分 | `draw_nodetail()` 已定义但**从未调用** | 无降级策略 |
| **索引结构** | 两级稀疏索引（每10万条一个节点）+ 二分查找 | 单层 `lower_bound` 二分查找 | 查找效率差异不大 |

#### [严重BUG] 跳跃遍历可能跳过大标注

在合并模式中，当累积小标注到合并块后，代码使用 `find_index_after_sample(merge_end_sample)` 进行跳跃遍历。该函数使用 `upper_bound` 找到第一个 `start_sample > merge_end_sample` 的标注。**问题在于：如果存在一个大标注（像素宽度 >= 4.0）其 `start_sample <= merge_end_sample`，该大标注会被跳跃跳过，永远不会被绘制。**

- 标注 A: start=100, end=200（小标注，像素宽度 < 4）
- 标注 B: start=150, end=1000（大标注，像素宽度 >= 4，与A重叠）
- 标注 C: start=300, end=400（小标注）

1. 处理 A（小标注），加入合并块，`merge_end_sample` 约为 200

## 五、线程安全审查

### 5.1 annotation_at() 返回指针的生命周期

**核心问题**：`annotation_at()` 获取 shared_lock 后返回 `const Annotation*`，锁在函数返回时释放。指针在锁释放后是否仍然有效？

**分析**：
1. Annotation 对象是堆分配的（`new Annotation(...)` 在 `annotation_callback` 中），存储在 `_annotations` 向量中作为指针
2. `push_annotation()` 只做 `push_back`，不会删除或移动已有的 Annotation 对象。`vector` 的 `push_back` 可能导致 vector 重分配，但重分配移动的是指针（`Annotation*`），不是 Annotation 对象本身。因此 `annotation_at()` 返回的指针值（指向堆上的 Annotation 对象）在 `push_back` 后仍然有效
3. `clear()` 会删除所有 Annotation 对象（`delete p`），使指针悬空

**结论**：在 `clear()` 不与 `paint_mid()` 并发执行的前提下，`annotation_at()` 返回的指针是安全的。`clear()` 通过 `init()` 调用，`init()` 在 `do_decode_work()` 中执行（解码线程）。但 `init()` 在任何 `push_annotation` 之前调用，且 UI 线程在收到 `new_decode_data` 信号后才开始绘制，此时 `init()` 已完成。因此实际风险很低。

**[潜在风险]** 如果用户在绘制过程中触发新的解码（导致 `init()` 清空数据），理论上可能出现竞态。但这需要非常精确的时序，且 `RowData::_visitor_mutex` 的 unique_lock（clear 中）和 shared_lock（annotation_at 中）会互斥，确保不会在 `clear` 执行期间返回指针。真正的风险窗口是：`annotation_at()` 返回指针并释放锁之后、使用指针之前，`clear()` 获取锁并删除对象。这个窗口非常小，且需要 UI 线程和解码线程的精确交错。

### 5.2 get_visible_range() 与 annotation_at() 之间的间隙

`get_visible_range()` 和 `annotation_at()` 各自独立获取和释放 shared_lock。两次调用之间，解码线程可能 `push_annotation` 添加新标注。但这不会影响已有的索引和指针，只可能导致遗漏新标注（可接受）。不会导致崩溃或数据损坏。

### 3. `_decode_pixmap` 的使用方式

**文件**: `c:\Users\admin\Downloads\DSView-main_2026_4_27cppnb\PXView\pv\view\viewport.cpp` 第719-745行

`_decode_pixmap` 是一个独立的离屏缓冲区，专门用于解码 trace 的渲染。它的工作方式：

```
条件: decode_rebuild = rebuilt || _decode_needs_rebuild

如果 decode_rebuild == true:
    1. 创建新的透明 QPixmap(size())
    2. 创建 QPainter 绘制到 _decode_pixmap
    3. 遍历所有 SR_CHANNEL_DECODER 类型的 trace，调用 paint_mid()
    4. _decode_needs_rebuild = false

```

**关键设计**: 解码 trace 和逻辑信号使用**两个独立的pixmap**。这意味着：
- 逻辑信号重建时不需要重绘解码 trace
- 解码数据更新时不需要重绘逻辑信号
- 两者可以独立失效和重建

### 4. 解码 trace 重绘的触发条件

解码 trace 重绘（`_decode_pixmap` 重建）由以下条件触发：

| 触发源 | 代码路径 | 导致 `_decode_needs_rebuild=true` |
|--------|----------|----------------------------------|
| **新解码数据到达** | `DecodeTrace::on_new_decode_data()` → `_view->viewport_update()` → `_time_viewport->set_decode_dirty()` | 是 |
| **解码完成** | `DecodeTrace::on_decode_done()` → `_view->viewport_update()` → `_time_viewport->set_decode_dirty()` | 是 |
| **滚动/缩放** | `View::set_scale_offset()` / `View::h_scroll_value_changed()` → `viewport_update()` → `set_decode_dirty()` | 是 |
| **视图参数变化** | scale/offset/signalHeight/vOffset 变化 → `rebuilt=true` → `decode_rebuild=true` | 是（通过 `rebuilt`） |
| **鼠标移动** | `Viewport::mouseMoveEvent()` → `update()` → `paintEvent()` → `paintSignals()` | 否（不重建，只blit缓存） |

**重要发现**: `viewport_update()` 每次都调用 `set_decode_dirty()`，所以**滚动和缩放也会触发解码pixmap重建**。鼠标移动等不经过 `viewport_update()` 的操作则不会重建解码pixmap。

### 完整重绘代价分析

当一条新 annotation 到达时，**完整的操作链**是：

1. **DecoderStack 工作线程**发出 `new_decode_data` 信号（受 `notify_cnt` 间隔控制）
2. **DecodeTrace::on_new_decode_data()** 节流到 50 FPS
3. **viewport_update()** 标记 `_decode_needs_rebuild=true`，调度全窗口重绘
4. **paintEvent() → doPaint()** 执行全量渲染：
   - `check_update()` — 轻量检查
   - `paint_back()` — 所有 trace 的背景（包括 DecodeTrace 的背景线和标题）
   - `paintSignals()`:
     - 逻辑信号：如果参数没变，只 blit 缓存（廉价）；否则重建（昂贵）
     - **解码信号：每次都重建整个 `_decode_pixmap`**，因为 `_decode_needs_rebuild` 被设为 true
     - 重建过程：遍历所有 DecodeTrace，每个 trace 遍历所有可见 Row 和 Annotation
   - `paintCursors()`, `paint_fore()` 等

**核心代价问题**：即使只有一个新 annotation 到达，`_decode_pixmap` 也会被完全重建——创建新的全尺寸 QPixmap、填充透明、遍历所有解码 trace 的所有 annotation 重新绘制。没有增量更新机制。不过，由于 `_pixmap`（逻辑信号）和解码pixmap是分离的，至少逻辑信号不需要重建。

**节流保护**：`on_new_decode_data()` 限制为最多 50 FPS（20ms 间隔），`data_updated()` 限制为最多 ~60 FPS（16ms 去重），这防止了高频解码数据导致的过度重绘。

根据对完整渲染管线的深入分析，问题的本质是：

**每次新 annotation 到达 → 重建整个 `_decode_pixmap` → 遍历所有可见 annotation 重新绘制**

无论缩放级别如何，这个全量重建都会发生。缩到最小时可见 annotation 更多，每帧代价更大。

## 多种解决方案

### 方案1：增量式 decode pixmap 更新（推荐）

**核心思路**：不重建整个 `_decode_pixmap`，只在现有 pixmap 上追加绘制新增的 annotation。

**实现要点**：
- 每个 `RowData` 记录 `_last_rendered_count`（上次渲染时已绘制的 annotation 数量）
- `on_new_decode_data()` 时，只在 `_decode_pixmap` 上绘制 `_last_rendered_count` 之后新增的 annotation
- 仅在视图参数变化（scroll/zoom/scale）时才全量重建

**优点**：解码期间每帧只绘制少量新增 annotation，代价接近 O(1)
**缺点**：滚动/缩放时仍需全量重建；需要处理 annotation 在行尾追加而非中间插入的假设

---

### 方案2：LOD 概览图（Level of Detail）

**核心思路**：当 `min_annWidth < 阈值` 时，不遍历 annotation，直接绘制预计算的概览色带。

**实现要点**：
- 解码完成（或每处理 N 个 annotation）后，预计算每行的"像素级概览"：对每个像素列，统计落入该列的 annotation 的主色调
- 存储为一个 `QImage`（宽度=总像素宽度，高度=行数×行高）
- 缩到最小时直接 blit 概览图，O(1) 代价
- 放大时切换到逐条绘制

**优点**：缩到最小时渲染代价极低；概览图可缓存复用
**缺点**：需要额外内存存储概览图；缩放时需在两种模式间切换；预计算有延迟

---

### 方案3：分离解码渲染频率与视口刷新频率

**核心思路**：解码 pixmap 的重建不与视口 paintEvent 同步，而是独立以低频率更新。

**实现要点**：
- `on_new_decode_data()` 不再调用 `viewport_update()`，而是启动一个 100-200ms 的定时器
- 定时器触发时才重建 `_decode_pixmap`，然后调用 `viewport->update()` blit 新 pixmap
- 滚动/缩放时立即重建（保证交互响应）
- 解码期间视口以正常 60 FPS 刷新，但 decode pixmap 以 5-10 FPS 更新

**优点**：实现简单；解码期间 CPU 占用大幅降低；不影响交互流畅度
**缺点**：解码期间 annotation 更新有视觉延迟（100-200ms）；用户可能感觉"解码结果出现慢"

---

### 方案4：解码期间降级渲染

**核心思路**：解码进行中时，不渲染 annotation 细节，只显示进度条和"解码中"提示。

**实现要点**：
- `on_new_decode_data()` 只更新进度条，不触发 decode pixmap 重建
- 解码完成（`on_decode_done()`）时一次性全量渲染所有 annotation
- 类似于已有的 `draw_nodetail()` 方法（已定义但从未调用）

**优点**：实现最简单；解码期间零渲染开销
**缺点**：用户在解码过程中看不到任何 annotation 结果，体验差；长时间解码时用户无法预览

---

### 方案5：分帧渐进渲染

**核心思路**：每帧只渲染一部分 annotation，多帧累积完成全部渲染。

**实现要点**：
- 维护一个"已渲染到第 N 个 annotation"的游标
- 每次 `paintMid()` 只渲染接下来的 M 个 annotation（如 1000 个）
- 未渲染完时设置一个短定时器（如 16ms）触发下一帧继续
- 视口每帧都能快速响应，annotation 逐渐"填充"出来

**优点**：每帧渲染时间可控；用户能看到渐进式填充效果
**缺点**：实现复杂；需要处理滚动/缩放中断渐进渲染的情况；视觉上可能闪烁

---

### 方案6：预渲染瓦片缓存

**核心思路**：将 annotation 按时间范围分块为瓦片，预渲染到 QPixmap，重绘时只 blit 瓦片。

**实现要点**：
- 将整个采样范围划分为固定大小的瓦片（如每 10K 样本一个瓦片）
- 每个 `RowData` 维护一个 `map<tile_index, QPixmap>` 缓存
- 新 annotation 到达时，只重新渲染受影响的瓦片
- 视口重绘时，计算可见范围内的瓦片，blit 对应的 QPixmap

**优点**：滚动时只需 blit 已缓存的瓦片，极快；新数据只影响少量瓦片
**缺点**：内存开销大（每个瓦片一个 QPixmap）；缩放时瓦片失效需全部重建；实现复杂

---

### 方案7：降低解码期间的通知频率

**核心思路**：当前 50 FPS 节流仍然太高，进一步降低解码期间的刷新频率。

**实现要点**：
- 解码进行中时，将 `on_new_decode_data()` 的节流间隔从 20ms 提高到 100-200ms
- 同时在 `DecoderStack` 中将 `notify_cnt` 从 `total/1000` 提高到 `total/100`
- 减少信号发射次数和重绘次数

**优点**：一行代码即可实现；立竿见影
**缺点**：治标不治本；每帧的渲染代价仍然随 annotation 数量增长

### LOD 实现方案

**数据结构**：每行维护一个 `QImage`（宽度 = 总样本数 / 采样率 × 缩放基准），高度 = 行高。解码完成时预计算：每个像素列压入离它最近的 annotation 的颜色，像素列无 annotation 则为透明。

**paint_mid 逻辑**：
```
若 total_annotations > 10000 且 min_annWidth < 4px:
  → 不遍历 annotation
  → 直接从 LOD QImage 中截取当前视口的矩形区域
  → drawImage 到 _decode_pixmap  ← O(1)，只取决于屏幕像素数
否则：
  → 走当前逐条绘制逻辑（此时 annotation 少，O(N) 可忽略）
```

**内存开销**：假设 100M 样本，每像素代表 100 样本，则概览图宽度 = 1,000,000 像素。若行高 20px，RGBA 格式，每行 ≈ 80MB。对于百万级 annotation 的场景，这是可接受的（不会同时有很多行）。

## 唯一能彻底解决的方案：解码期间完全不重绘 decode pixmap

**核心思路**：解码进行中时，decode pixmap 不随新数据更新。只在解码完成时一次性全量渲染。

### 具体实现

1. **解码进行中**：`on_new_decode_data()` 只更新进度条，不触发 decode pixmap 重建
   - 进度条是一个独立的 UI 元素（已有 `decoded_progress()` 信号）
   - 或者在一个小区域显示"解码中 XX%"文字

2. **解码完成**：`on_decode_done()` 一次性全量重建 decode pixmap

3. **用户交互**：滚动/缩放时如果解码还在进行，可以：
   - 选项 A：不响应（禁用滚动/缩放直到解码完成）

### 2. DoubleBuffering 是否缓存解码结果？

**答案：没有缓存，每帧都完全重建。**


它直接在传入的 `painter` 上绘制，没有先画到离屏缓冲区再 blit。每次 `paint()` 被调用时，`DrawDecode()` 都会被完整执行。

### 3. 重绘频率与节流机制

**解码期间的重绘频率约为每 200ms 一次。**

节流机制通过 `DecodeContent.qml` 中的 `decodeRefreshTimer` 实现：

- **interval: 200ms** -- 解码进度信号到来时，如果 timer 已在运行则不重复启动（`if(!decodeRefreshTimer.running)`），自然形成约 5fps 的节流
- 解码进度信号 `sendDecodeSchedule` 的发送频率取决于数据块大小（`_MAX_CHUNK_SIZE = 64KB`）和 `scheduleIndex` 计算，大约每处理一定比例的数据发送一次

**采集期间**的实时刷新频率约为每 25ms 一次（40fps），通过 `ChannelsView.qml` 中的 `refreshChannelTimer`（interval: 25ms）实现，同样有 `if(!refreshChannelTimer.running)` 的去重保护。

### 4. 新注解到达时是全量重建还是增量更新？

**答案：每次重绘都是全量重建，没有增量更新。**

`DrawDecode()` 方法（`double_buffering.cpp:110-375`）的工作流程：

1. 遍历 `DecodeController::m_rowList` 的所有行
2. 对每个可见行，使用**二分查找**定位当前视口范围内的起始数据索引
3. 从该索引开始，顺序遍历所有注解数据，逐个绘制

虽然有二分查找优化（`findDecodeRowDataNode` 和 `findDecodeRowFirstData`），但绘制本身是**从视口起始位置到视口结束位置的全部注解**，没有任何缓存或增量机制。每次 `DrawDecode()` 调用都会重新绘制视口内所有可见的解码注解。

**注解数据的写入**是增量的：`_output_callback` 回调函数将新注解追加到 `DecodeRow::data` 列表，并使用 `tmpData` + `Insert_sort` 做批量排序插入。但渲染侧读取时是全量遍历。

| `refreshChannelTimer` (25ms) | ChannelsView.qml | 采集期间节流刷新 |

### 总结：atk-logic 是否避免了"每条新注解都全量重建"的问题？

**没有避免。** atk-logic-master 的解码渲染存在以下特征：

1. **每帧全量重建**：`DrawDecode()` 每次都从 `m_rowList` 中读取所有数据并重新绘制视口内的全部注解，没有离屏缓存
2. **节流而非去重**：通过 200ms 定时器节流，将解码进度信号的频率降低到约 5fps，但每次触发仍然是全量重绘
3. **二分查找是唯一的优化**：`findDecodeRowDataNode` 和 `findDecodeRowFirstData` 使用二分查找快速定位视口起始位置，避免了遍历全部数据，但视口内的数据仍然是逐个绘制
4. **DoubleBuffering 名不副实**：类名叫"双缓冲"但实际没有做任何缓冲，只是直接绘制到传入的 painter 上
5. **没有增量更新机制**：新注解到达后，不会只绘制新增部分，而是重绘整个视口

**唯一的缓解措施**是 200ms 的定时器节流，使得解码期间不会因为每条新注解都触发一次重绘，而是将多条注解的更新合并到一次重绘中。但这仍然是"全量重建"，只是频率降低了。
