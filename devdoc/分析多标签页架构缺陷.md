## 一、架构总览

DSView 的多标签页架构采用 **"TabWidget + TabContext + SessionManager"** 三层设计，核心思路是：每个标签页对应一个 `TabContext`，每个 `TabContext` 持有一个 `View`（视图）和一个 `SessionDocument`（文档数据），所有标签上下文由 `SessionManager` 统一管理。标签页 UI 层使用自定义的 `DraggableTabWidget` / `DraggableTabBar`，支持拖拽分离、右键菜单、重命名等操作。

## 四、标签页生命周期

1. **创建**：`on_new_tab_requested()` → 新建 `View` + `SessionDocument` → `SessionManager::create_context()` 创建 `TabContext` → `add_tab()` 添加到 UI
2. **切换**：`on_tab_changed()` → 旧标签 `deactivate()`（变 HISTORICAL）→ 新标签 `activate()`（设为 LIVE，绑定数据源和 Dock 控件）
3. **分离**：拖拽标签到栏外 → `DraggableTabBar::detachTab` → `DraggableTabWidget::onDetachTab` 创建 `SubMainFrame` 浮动窗口 → `MainWindow::on_tab_detach` 从列表移除上下文
4. **重新附加**：关闭浮动窗口 → `SubMainFrame::windowClosed` → `DraggableTabWidget::onDetachedWindowClosed` 将 widget 重新 addTab → `MainWindow::on_tab_attached` 恢复 TabContext
5. **关闭**：点击关闭按钮 → `DraggableTabWidget::tabCloseRequested` → `MainWindow::remove_tab` → 销毁 View、注销 Document、销毁 TabContext（至少保留一个标签）
6. **重命名**：双击标签 → `DraggableTabBar::tabRenameRequested` → `DraggableTabWidget::onTabRenameRequested` 弹出内联编辑器 → `tabRenamed` 信号更新 TabContext 标题

## 五、设计要点总结

- **一个 SigSession，多个 TabContext**：所有标签共享同一个采集会话，但每个标签有独立的 `SessionDocument`（文档数据）和 `View`（视图）
- **LIVE/HISTORICAL 状态切换**：当前活跃标签为 LIVE，其余为 HISTORICAL，通过 `activate()`/`deactivate()` 切换数据源
- **标签样式区分**：LIVE 标签显示绿色圆点前缀，有数据标签灰色文字，无数据标签暗灰文字
- **拖拽分离/重新附加**：通过 `detached_ctx` 属性在 View 对象上保存分离的上下文指针，实现分离后重新附加时恢复状态
- **SessionManager 单例**：统一管理所有上下文的生命周期，区分主窗口上下文和分离窗口上下文

- 所有标签页共享同一个 `SigSession` 实例（`_session`）
- 每个标签页拥有独立的 `View`、`SessionDocument` 和 `TabContext`
- `TabContext` 是三者之间的绑定纽带（[tabcontext.h#L42-L81](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/tabcontext.h#L42-L81)）

`TabContext` 有两种状态：
- **LIVE** — 当前活跃标签，正在实时采集
- **HISTORICAL** — 非活跃标签，显示历史快照数据

切换标签时的流程（[mainwindow.cpp:2641-2683](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/mainwindow.cpp#L2641-L2683)）：
1. 旧标签 `deactivate()` → 状态变为 HISTORICAL
2. 新标签 `activate()` → 状态变为 LIVE
3. Dock 控件 `unbind_context()` / `bind_context()` 切换绑定

`TabContext::activate()`（[tabcontext.cpp:61-79](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/tabcontext.cpp#L61-L79)）：
```cpp
void TabContext::activate()
{
    _session->set_active_document(_document);
    _state = LIVE;
    if (_document && _document->has_data()) {
        _view->set_data_document(_document);  // 从文档读取数据
    } else {
        _view->set_data_source(_session);     // 从 Session 实时数据读取
        _view->set_signal_data_from_source(_session);
    }
    _view->update_scale_offset();
    _view->signals_changed(nullptr);

```

### 五、Signal/Slot 连接关系

#### 1. SigSession → MainWindow（通过 ISessionCallback 接口）

`SigSession` 通过 `_callback` 指针（类型为 `ISessionCallback*`）回调 `MainWindow`。`MainWindow` 实现了 `ISessionCallback` 接口（[mainwindow.h#L193-L209](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/mainwindow.h#L193-L209)）。

关键回调路径：
```
SigSession._callback->data_updated()     → MainWindow.data_updated()     → EventObject.data_updated()     → MainWindow.on_data_updated()     → View.data_updated()
SigSession._callback->signals_changed()  → MainWindow.signals_changed()  → EventObject.signals_changed()  → MainWindow.on_signals_changed()  → View.signals_changed()
SigSession._callback->frame_began()      → MainWindow.frame_began()      → EventObject.frame_began()      → MainWindow.on_frame_began()      → View.frame_began()
SigSession._callback->frame_ended()      → MainWindow.frame_ended()      → EventObject.frame_ended()      → MainWindow.on_frame_ended()      → View.receive_end()
SigSession._callback->receive_trigger()  → MainWindow.receive_trigger()  → EventObject.receive_trigger()  → MainWindow.on_receive_trigger()  → View.receive_trigger()
```

**注意**：`ISessionCallback` 的实现在 `MainWindow` 中先触发 `EventObject` 的 Qt 信号，再由信号槽机制转到对应的 slot。这是因为 `SigSession` 的回调可能来自采集线程，需要通过 Qt 信号槽机制安全地切换到 UI 线程。

### 八、关键设计要点

1. **单 Session 多标签**：整个应用只有一个 `SigSession` 实例，但可以有多个标签页（TabContext），每个标签页有独立的 `SessionDocument` 存储历史数据快照。

2. **双缓冲采集**：`SigSession` 使用两个 `SessionData` 实现双缓冲，采集线程和 UI 线程可以并行工作。

3. **线程安全通信**：`SigSession` 的采集回调通过 `ISessionCallback` → `MainWindow` → `EventObject`(Qt信号) → `MainWindow slot` → `View` 的路径，确保跨线程安全。

4. **数据源切换**：View 通过 `effective_data_source()` 动态决定从 `SessionDocument`（历史数据）还是 `SigSession`（实时数据）读取，实现同一 View 组件在不同标签页的复用。

5. **Dock 共享与上下文绑定**：Dock 窗口不属于任何标签页，切换标签时通过 `IContextAware::bind_context()` / `unbind_context()` 动态切换关联的 `TabContext`。

### 二、标签页切换时 Dock 数据的完整变化流程

```
   ├── SamplingBar::unbind_context()

   ├── SamplingBar::bind_context(new_ctx)

   ├── SearchDock::bind_context(new_ctx)       → 从新 document 读取 _dock_search_pattern
   ├── ProtocolDock::bind_context(new_ctx)     → 切换 _view, 重建协议层
   ├── DeviceOptionsDock::bind_context(new_ctx) → 从新 document 读取 _dock_device_options_session
```

### 三、架构缺陷分析

#### 缺陷 1：Dock 状态保存/恢复不一致 — ProtocolDock 的 unbind_context 是空实现

[ProtocolDock::unbind_context()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/protocoldock.cpp#L258-L260) 是**空函数体**，这意味着当从 Tab A 切换到 Tab B 时，Tab A 的协议解码器状态不会被保存。虽然协议数据绑定在 `SessionDocument` 的 `DecoderStack` 上（不需要额外保存），但 `ProtocolDock` 的 UI 状态（如搜索关键词、协议层展开/折叠状态、当前选中的协议项等）会丢失。

```cpp
void ProtocolDock::unbind_context()
{
    // 空实现！UI 状态未保存
}
```

**影响**：切换回 Tab A 时，ProtocolDock 的 UI 会被 `rebuild_protocol_layers()` 完全重建，用户之前的交互状态（滚动位置、选中项、搜索文本等）丢失。

---

#### 缺陷 2：DeviceOptionsDock 的状态保存与硬件状态耦合

[DeviceOptionsDock::unbind_context()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/deviceoptionsdock.cpp#L1001-L1007) 在保存时调用 `get_session()`，而 `get_session()` 直接读取**当前硬件设备**的配置（工作模式、通道使能、模拟参数等），而不是读取该标签页对应的配置：

```cpp
void DeviceOptionsDock::unbind_context()
{
    if (_context && _context->document() && _device_agent && _device_agent->have_instance()) {
        // 问题：get_session() 读取的是硬件当前状态，不是该标签页的状态
        _context->document()->_dock_device_options_session = get_session();
    }
    _context = nullptr;
}
```

**影响**：如果用户在 Tab A 修改了设备配置后切换到 Tab B，Tab A 保存的"设备配置"实际上是 Tab B activate 后可能已经改变的硬件状态，而不是 Tab A 当时的配置。这是因为硬件只有一套，`get_session()` 读到的永远是当前硬件的实时值。

---

#### 缺陷 3：单 SigSession + 单硬件设备导致多标签页数据冲突

所有标签页共享同一个 `SigSession` 和同一个硬件设备。当采集帧结束时，[on_frame_ended()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp) 只将数据复制到**当前活跃标签**的 `SessionDocument`：

```cpp
void MainWindow::on_frame_ended()
{
    pv::TabContext *ctx = current_context();
    if (ctx && ctx->document()) {
        _session->copy_data_to_document(ctx->document());
        ctx->activate();
    }
    current_view()->receive_end();
}
```

**影响**：
- 非活跃标签永远无法获取新的采集数据
- 只有一个标签页可以是 LIVE 状态，其他标签页只能是 HISTORICAL
- 无法实现"后台标签页持续采集"的场景
- 如果用户想在两个标签页分别用不同配置采集，必须来回切换，操作繁琐

---

#### 缺陷 4：unbind_context 的调用顺序问题 — 先 unbind 所有 Dock 再 bind

在 [on_tab_changed()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2659-L2676) 中，所有 Dock 先统一 `unbind_context()`，再统一 `bind_context()`。这意味着在 unbind 阶段，某些 Dock 可能需要依赖其他 Dock 的状态，但这些状态已经被清空了。

```cpp
// 先全部 unbind
_sampling_bar->unbind_context();
_measure_widget->unbind_context();
_search_widget->unbind_context();
_protocol_widget->unbind_context();
_device_options_widget->unbind_context();
_trigger_widget->unbind_context();
_dso_trigger_widget->unbind_context();

// 再全部 bind
_sampling_bar->bind_context(new_ctx);
_measure_widget->bind_context(new_ctx);
// ...
```

**影响**：
- 如果 Dock 之间有依赖关系（例如 DeviceOptionsDock 的配置影响 TriggerDock 的选项），在 unbind 阶段可能读取到不一致的状态
- 中间存在一个"所有 Dock 都没有绑定上下文"的窗口期，如果此时有异步事件（如设备回调），可能导致 Dock 操作空指针

---

#### 缺陷 5：SessionManager 与 MainWindow 的 TabContext 列表重复管理

`MainWindow` 持有 `QList<TabContext*> _tab_contexts`，`SessionManager` 持有 `std::vector<TabContext*> _contexts`。两处独立维护同一组 TabContext 指针，但同步逻辑分散在不同方法中：

- [add_tab()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2564-L2571)：只往 `_tab_contexts` 添加，不通知 SessionManager
- [on_tab_detach()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2685-L2713)：从 `_tab_contexts` 移除，并调用 `SessionManager::detach_context()`
- [on_tab_attached()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2715-L2729)：往 `_tab_contexts` 添加，并调用 `SessionManager::attach_context()`

**影响**：
- `add_tab()` 没有通知 SessionManager，但 `create_context()` 已经在 SessionManager 中注册了，所以新标签页的添加路径不一致
- 两个列表可能因 bug 而不同步，导致悬空指针或内存泄漏
- SessionManager 作为单例的设计意图是统一管理，但 MainWindow 又维护了一份独立列表，职责不清

---

#### 缺陷 6：TabContext 的 detached_ctx 属性使用 QVariant 传递指针不安全

在 [on_tab_detach()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2711) 中，分离标签时将 TabContext 指针通过 `QVariant::fromValue((quintptr)ctx)` 存储在 View 的属性中：

```cpp
ctx->view()->setProperty("detached_ctx", QVariant::fromValue((quintptr)ctx));
```

在 [on_tab_attached()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2722) 中，通过 `reinterpret_cast` 恢复：

```cpp
pv::TabContext *ctx = reinterpret_cast<pv::TabContext*>(prop.value<quintptr>());
```

**影响**：
- 如果分离的窗口被关闭时 TabContext 已经被销毁（例如程序退出流程），`reinterpret_cast` 会产生悬空指针
- 没有生命周期保护机制，无法检测指针是否仍然有效
- 使用 `quintptr` 作为中间类型绕过了 Qt 的类型安全系统

---

#### 缺陷 7：remove_tab 中临时断开信号连接存在竞态风险

在 [remove_tab()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\mainwindow.cpp#L2591-L2592) 中：

```cpp

_tab_widget->removeTab(index);
```

临时断开 `currentChanged` 信号是为了避免 `removeTab()` 触发 `on_tab_changed()` 导致状态混乱。但之后没有重新连接的代码——实际上依赖的是 `removeTab()` 之后 `setCurrentIndex` 自动触发 `on_tab_changed`，但此时信号已断开。

**影响**：删除标签页后，新的活跃标签页的 Dock 绑定可能不完整，因为没有走 `on_tab_changed` 的完整流程。虽然后面有 `_tab_contexts[_current_tab_index]->activate()`，但缺少了 Dock 的 `unbind_context` / `bind_context` 调用。

---

#### 缺陷 8：Dock 可见性状态未按标签页保存

Dock 的可见性（哪个 Dock 当前显示）由 `TrigBar` 和 `AppConfig::DockOptions` 控制，按**设备模式**（LOGIC/DSO/ANALOG）存储，而不是按**标签页**存储。这意味着：

- 用户在 Tab A 打开了 ProtocolDock，切换到 Tab B 时 ProtocolDock 仍然显示
- 不同标签页可能需要不同的 Dock 布局（例如 Tab A 需要看协议解码，Tab B 需要看触发器），但当前无法实现
- `DockOptions` 没有保存到 `SessionDocument` 中

#### 缺陷 9：SearchDock 的搜索结果在标签切换时被清空

[SearchDock::unbind_context()](file:///c:/Users/admin/Downloads\DSView-main_2026_4_27cppnb\DSView\pv\dock\searchdock.cpp#L254-L265) 会清空搜索结果：

#### 4.2 FPGA 重配置 — 最重的硬件操作

[dsl.c:1296-1485](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/libsigrok4DSL/hardware/DSL/dsl.c#L1296-L1485)

FPGA 配置是一个**多步骤的同步 USB 操作**，流程如下：
1. **step0**: 拉低 PROG_B（复位 FPGA）
2. **step1**: 关闭 LED 指示灯
3. **step2**: 拉高 PROG_B
4. **step3**: 轮询等待 INIT_B 变高（**忙等待循环**）
5. **step4-8**: 分块发送 FPGA bitstream 文件到设备
6. **step9**: 轮询等待 FPGA_DONE 变高（**忙等待循环**）

```c
SR_PRIV int dsl_fpga_config(struct libusb_device_handle *hdl, const char *filename)
{
    // step0: assert PROG_B low
    // step1: turn off GREEN/RED led
    // step2: assert PROG_B high
    // step3: wait INIT_B go high (busy loop!)
    while(1) {
        command_ctl_rd(hdl, rd_cmd);
        if (rd_cmd_data & bmFPGA_INIT_B) break;
    }
    // step4-8: send bitstream chunks
    // step9: check FPGA_DONE bit (busy loop!)
}
```

## 切换 Tab 时切换硬件配置的可行性分析

**结论：部分可行，但需要分层处理，不同配置项的可行性和代价差异很大。**

### 一、硬件配置项分层

根据对代码的深入分析，硬件配置项可以按"切换代价"分为三层：

```
┌─────────────────────────────────────────────────────────────────┐
│  第1层：纯软件配置（零硬件代价，完全可行）                         │
│  ├── 触发器配置（触发值/阶段/逻辑/位置）                          │
│  ├── 搜索模式（SearchDock pattern）                              │
│  ├── 测量行配置（MeasureDock cursor rows）                       │
│  └── 协议解码器配置（DecoderStack）                               │
├─────────────────────────────────────────────────────────────────┤
│  第2层：轻量硬件配置（需写硬件寄存器，但不需要停采集，基本可行）     │
│  ├── 通道使能（probe->enabled）→ SR_CONF_PROBE_EN               │
│  ├── 操作模式（buffer/stream）→ SR_CONF_OPERATION_MODE          │
│  ├── 通道模式（8/16/32ch）→ SR_CONF_CHANNEL_MODE               │
│  ├── 模拟参数（vdiv/coupling/map_default）                       │

│  ├── 阈值电压变更 → FPGA 重配置（忙等待+USB传输bitstream）        │
│  └── 采样率/采样深度变更（部分场景需停采集）                      │
└─────────────────────────────────────────────────────────────────┘
```

### 二、各层可行性详细分析

#### 第1层：纯软件配置 ✅ 完全可行

当前代码已经基本实现了这层切换：

- **TriggerDock**：[get_session()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/triggerdock.cpp#L418) / [set_session()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/triggerdock.cpp#L470) 完整序列化/反序列化触发器配置
- **DsoTriggerDock**：同上
- **SearchDock**：保存 `_dock_search_pattern`
- **MeasureDock**：保存 `_dock_measure_*` 字段

**唯一问题**：这些配置在 `unbind_context()` 时保存到 `SessionDocument`，但 `get_session()` 读取的是**当前 UI 控件状态**，不是硬件状态。由于这些是纯软件配置，UI 状态 = 实际状态，所以没有矛盾。

#### 第2层：轻量硬件配置 ⚠️ 可行但需谨慎

这是你提出的核心问题。让我分析切换流程：

**场景**：Tab A（LOGIC, 8通道, buffer模式）→ Tab B（LOGIC, 16通道, stream模式）

切换时需要执行的操作：

```cpp
// 1. 保存 Tab A 的配置到其 SessionDocument
TabA_doc._dock_device_options_session = DeviceOptionsDock::get_session();

// 2. 从 Tab B 的 SessionDocument 恢复配置
QJsonObject &saved = TabB_doc._dock_device_options_session;
DeviceOptionsDock::set_session(saved);
```

[DeviceOptionsDock::set_session()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/deviceoptionsdock.cpp#L1064-L1114) 内部会调用：

```cpp
_device_agent->set_config_int16(SR_CONF_OPERATION_MODE, ...);  // 写硬件
_device_agent->set_config_int16(SR_CONF_CHANNEL_MODE, ...);    // 写硬件
update_view();                                                   // 重建UI
// 遍历通道设置 enabled, vdiv, coupling 等
```

**可行性分析**：

| 维度 | 评估 |
|------|------|
| 是否需要停采集 | ❌ 不需要（`reload()` 内部检查 `_is_working`，如果正在采集则跳过） |
| 是否清空数据 | ❌ 不清空（`reload()` 保留数据，只有 `init_signals()` 才清空） |
| 信号重建 | ⚠️ 需要 `reload()` + `rebuild_signals()`，有 UI 闪烁 |
| 硬件操作 | ⚠️ 写 USB 寄存器，有毫秒级延迟 |
| 采集中切换 | ⚠️ 通道使能变更会触发 `DSV_MSG_DEVICE_OPTIONS_UPDATED` → `reload()`，但 `reload()` 在采集中被跳过，导致**硬件配置和软件状态不同步** |

**关键问题**：

1. **采集中切换 Tab 的矛盾**：如果正在 Tab A 采集，切换到 Tab B 时调用 `set_session()` 改变了硬件通道配置，但 `SigSession::reload()` 检测到 `_is_working == true` 会直接 return，信号列表不会更新。结果：硬件已经按 Tab B 的配置运行，但软件侧的信号列表还是 Tab A 的。

2. **`get_session()` 读取的是硬件实时状态**：当前 [DeviceOptionsDock::get_session()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/dock/deviceoptionsdock.cpp#L1009-L1062) 从 `_device_agent` 读取硬件当前值，而不是从 UI 控件读取。这意味着在 `unbind_context()` 时保存的是硬件当前值，而非该标签页的"期望配置"。如果之前有配置切换失败或被覆盖，保存的就是错误值。

3. **信号列表全局共享**：`SigSession::_signals` 是全局唯一的，切换 Tab 改变硬件配置后，所有 Tab 的 View 都会看到新的信号列表（因为 `View::rebuild_signals()` 从 `_data_source->get_signals()` 克隆）。非活跃 Tab 的信号列表会被意外改变。

#### 第3层：重量硬件配置 ❌ 代价极大，不建议

**场景**：Tab A（LOGIC模式）→ Tab B（DSO模式）

[switch_work_mode()](file:///c:/Users/admin/Downloads/DSView-main_2026_4_27cppnb/DSView/pv/sigsession.cpp#L2342-L2384) 的硬性要求：

```cpp
bool SigSession::switch_work_mode(int mode)
{
    assert(!_is_working);  // ← 硬断言：必须停采集！
    // ...
    _capture_data->clear();  // 清空所有数据
    _view_data->clear();
    init_signals();           // 完全重建信号
    broadcast_msg(DSV_MSG_DEVICE_MODE_CHANGED);
}
```

**不可行的原因**：

1. **必须停止采集**：`assert(!_is_working)` 是硬断言，如果正在采集会直接崩溃
2. **数据全部清空**：`_capture_data->clear()` + `_view_data->clear()` 清空了双缓冲区的所有数据
3. **信号完全重建**：`init_signals()` 从零创建信号列表，不保留任何状态
4. **全局副作用**：`DSV_MSG_DEVICE_MODE_CHANGED` 触发 `reset_all_view()`，影响所有视图组件
5. **FPGA 间接重配置**：虽然 `switch_work_mode()` 不直接触发 FPGA 重配置，但下次启动采集时会根据新模式加载不同的 FPGA bitstream
6. **切换延迟大**：涉及 USB 通信 + 信号重建 + 视图重布局，用户可感知的卡顿

### 三、核心矛盾：信号列表全局唯一

这是整个方案最根本的障碍。当前架构中 `SigSession::_signals` 是全局唯一的：

```
SigSession._signals  ←→  硬件当前配置
       ↓
View.rebuild_signals()  ← 从 _data_source->get_signals() 克隆
       ↓
所有 Tab 的 View 都看到同一组信号
```

当切换 Tab 改变硬件配置时：
- Tab A 的 View 有 8 个 LogicSignal
- 切换到 Tab B，硬件改为 16 通道
- `reload()` 重建 `_signals` 为 16 个 LogicSignal
- Tab A 的 View 的 `_own_signals` 已经是旧的 8 个信号克隆
- 但 Tab A 的 `SessionDocument` 保存的是 8 通道的数据快照
- 切回 Tab A 时，`activate()` 调用 `_view->set_data_document(_document)`，但 View 的信号列表已经被改成了 16 通道

**结果**：Tab A 的历史数据（8通道）和当前信号列表（16通道）不匹配，导致显示异常。

### 四、可行的改进方案

#### 方案 A：限制多标签页为同模式（推荐，改动最小）

**核心思路**：所有标签页必须使用相同的 `work_mode`，切换 Tab 时只切换第1层和第2层配置，不切换 `work_mode`。

```
┌────────────────────────────────────────────────────────────┐
│  切换 Tab 时的配置恢复策略                                    │
│                                                            │
│  第1层（纯软件）：完全恢复 ✅                                │
│  ├── 触发器配置：set_session(saved_trigger)                 │
│  ├── 搜索模式：_pattern = saved_pattern                    │
│  ├── 测量行：从 saved JSON 恢复                             │
│  └── 协议解码：从 SessionDocument 的 DecoderStack 恢复      │
│                                                            │
│  第2层（轻量硬件）：条件恢复 ⚠️                              │
│  ├── 仅在非采集状态下恢复                                    │
│  ├── 采集中只保存配置，不立即应用                             │
│  └── 下次启动采集时应用待生效的配置                           │
│                                                            │
│  第3层（重量硬件）：禁止切换 ❌                               │
│  ├── 新建标签页继承当前 work_mode                            │
│  ├── 不允许不同 work_mode 的标签页共存                       │
│  └── 如果要切换 work_mode，必须关闭所有标签页后重建           │
└────────────────────────────────────────────────────────────┘
```

**改动点**：

1. **修复 `get_session()` 的保存时机**：在 `unbind_context()` 时，应该保存 UI 控件状态而非硬件实时状态。或者更好的做法是：每次用户修改配置时立即保存到 `SessionDocument`，而不是等到 `unbind_context()` 才保存。

2. **增加"待生效配置"机制**：采集中切换 Tab 时，将目标配置标记为"待生效"，下次启动采集时自动应用：

```cpp
struct PendingConfig {
    QJsonObject device_options;
    QJsonObject trigger_config;
    bool has_pending = false;
};
// 存储在 SessionDocument 中
```

3. **信号列表隔离**：每个 `SessionDocument` 保存自己的信号配置快照（通道数、类型、使能状态），`View::rebuild_signals()` 从自己的 `SessionDocument` 读取而非从全局 `SigSession` 读取。

#### 方案 B：每个标签页独立信号列表（改动较大，更彻底）

**核心思路**：让 `SessionDocument` 持有独立的信号配置信息，View 从自己的 Document 重建信号，不再依赖全局 `SigSession::_signals`。

```
当前架构：
  SigSession._signals (全局) → View.rebuild_signals() → _own_signals

改进后：
  SessionDocument._signal_config (每标签独立) → View.rebuild_signals_from_doc() → _own_signals
  SigSession._signals (全局) → 仅用于实时采集标签
```

**改动点**：

1. **`SessionDocument` 增加信号配置字段**：

```cpp
struct SignalConfig {
    int work_mode;           // LOGIC/DSO/ANALOG
    int operation_mode;      // buffer/stream
    int channel_mode;        // 8/16/32ch
    struct ChannelConfig {
        int index;
        bool enabled;
        uint64_t vdiv;
        int coupling;
        // ...
    };
    std::vector<ChannelConfig> channels;
};
```

2. **`View` 增加从 Document 重建信号的能力**：

```cpp
void View::rebuild_signals_from_config(const SignalConfig &config)
{
    // 根据 config 创建对应的 Signal 对象
    // 不依赖 SigSession::_signals
}
```

3. **`TabContext::activate()` 时恢复硬件配置**：

```cpp
void TabContext::activate()
{
    _session->set_active_document(_document);
    _state = LIVE;
    
    // 恢复硬件配置（如果非采集状态）
    if (!_session->is_working()) {
        _document->apply_hardware_config();  // 写硬件寄存器
    }
    
    // 从 Document 重建信号（不依赖全局信号列表）
    _view->rebuild_signals_from_config(_document->signal_config());
    
    // 绑定数据源
    if (_document->has_data()) {
        _view->set_data_document(_document);
    } else {
        _view->set_data_source(_session);
    }
}
```

#### 方案 C：限制采集中切换 Tab（最保守，最安全）

**核心思路**：正在采集时，禁止切换到配置不同的标签页，或者切换时只恢复第1层配置，硬件配置保持不变。

```cpp
void MainWindow::on_tab_changed(int index)
{
    // ...
    if (_session->is_working()) {
        // 采集中：只恢复纯软件配置，不动硬件

        _search_widget->bind_context(new_ctx);
        _measure_widget->bind_context(new_ctx);

        // DeviceOptionsDock 不恢复硬件配置

    } else {
        // 非采集：完全恢复所有配置
        _device_options_widget->bind_context(new_ctx);
        _trigger_widget->bind_context(new_ctx);
        // ...
    }
}
```

**短期（方案A+C）**：先实现方案C作为安全兜底，再逐步实现方案A。具体步骤：

```
+-------------------+
|     SigSession    |  (应用层 - Qt GUI)
|  - _device_agent  |----> DeviceAgent (代理层)
```

核心约束：
- **单 session**：libsigrok4DSL 全局只有一个 `sr_session`
- **单活跃设备**：全局只有一个 `actived_device_instance`
- **单数据回调**：全局只有一个 `data_forward_callback`
- **单 SigSession 实例**：通过静态指针 `_session` 桥接回调
- 这些限制使得当前架构无法支持多设备同时采集

以下是对 DSView 项目中所有依赖 SigSession 的类和文件的完整分析。

### 一、当前架构的三层锁定

改多 Session 之前，必须理解当前架构存在**三层锁定**，每一层都是单实例设计：

```
┌─────────────────────────────────────────────────────────────────────┐
│  第1层：libsigrok4DSL（C 底层）— 全局单 session + 单活跃设备         │
│                                                                     │
│  session.c:   static struct sr_session *session = NULL;  ← 全局唯一 │
│  lib_main.c:  struct sr_dev_inst *actived_device_instance; ← 全局唯一│
│  lib_main.c:  lib_ctx.data_forward_callback;  ← 全局唯一数据回调    │
│  lib_main.c:  lib_ctx.collect_thread;  ← 全局唯一采集线程          │
│                                                                     │
│  代码注释: "There can only be one session at a time."               │
├─────────────────────────────────────────────────────────────────────┤
│  第2层：SigSession（Qt 应用层）— 全局单实例 + 静态自引用             │
│                                                                     │
│  sigsession.h:  static SigSession *_session;  ← 静态指针桥接回调    │
│  sigsession.h:  DeviceAgent _device_agent;  ← 内嵌成员，绑定硬件    │
│  sigsession.h:  SessionData *_view_data;  ← 双缓冲数据              │
│  sigsession.h:  SessionData *_capture_data;                         │
│  sigsession.h:  std::vector<view::Signal*> _signals;  ← 全局信号列表│
│                                                                     │
│  开发者 TODO: "Multiple concurrent sessions should be supported"     │
├─────────────────────────────────────────────────────────────────────┤
│  第3层：UI 组件层 — 32 个类直接持有 SigSession* 指针                │
│                                                                     │
│  6个Dock + 4个Toolbar + 10个Dialog + View及其7个子组件              │
│  + DecoderStack/SpectrumStack/MathStack + StoreSession + TabContext │
│  共 50 个源文件 include sigsession.h                                │
└─────────────────────────────────────────────────────────────────────┘
```

### 二、SigSession 成员变量分类 — 哪些可以多实例化

| 分类 | 成员变量 | 能否多实例 | 说明 |
|------|---------|-----------|------|
| **设备绑定** | `_device_agent` | ❌ 不能 | DeviceAgent 操作全局唯一活跃设备，多实例会冲突 |
| **设备绑定** | `_device_event` | ❌ 不能 | 设备事件全局唯一 |
| **采集状态** | `_is_working` | ❌ 不能 | 同一时刻只能有一个采集在运行 |
| **采集状态** | `_clt_mode`, `_is_stream_mode` | ❌ 不能 | 采集模式由硬件决定 |
| **采集状态** | `_is_instant`, `_capture_times` | ❌ 不能 | 采集参数全局唯一 |
| **数据缓冲** | `_view_data`, `_capture_data`, `_data_list` | ⚠️ 可分离 | 当前已通过 `SessionDocument` 实现了部分分离 |
| **信号列表** | `_signals` | ⚠️ 可分离 | 当前全局共享，可改为 per-document |
| **解码任务** | `_decode_tasks`, `_decoder_model`, `_decode_thread` | ⚠️ 可分离 | 可绑定到 SessionDocument |
| **频谱/利萨如/数学** | `_spectrum_traces`, `_lissajous_trace`, `_math_trace` | ⚠️ 可分离 | 可绑定到 SessionDocument |
| **定时器** | 6个 DsTimer | ⚠️ 可分离 | 部分是采集相关的（不能多实例），部分是 UI 刷新的（可多实例） |
| **回调** | `_callback` (ISessionCallback) | ✅ 可多实例 | 每个 Session 可以有自己的回调目标 |
| **消息监听** | `_msg_listeners` | ✅ 可多实例 | 每个 Session 可以有自己的监听器列表 |
| **文档管理** | `_active_document`, `_all_documents` | ✅ 可多实例 | 当前已支持多文档 |
| **保存状态** | `_is_saving`, `_save_start`, `_save_end` | ✅ 可多实例 | |
| **错误状态** | `_error`, `_error_pattern` | ❌ 不能 | 硬件错误全局唯一 |
| **静态指针** | `static SigSession *_session` | ❌ 根本障碍 | 全局唯一，用于桥接 C 回调 |

**结论**：SigSession 的成员大约 **40% 绑定硬件（不能多实例）、30% 可分离到 Document、30% 可多实例化**。

### 三、多 Session 架构的三个层次

根据改造深度，多 Session 可以有三种理解：

#### 层次 A：伪多 Session（不改 libsigrok，只改应用层）

**思路**：保持一个 SigSession + 一个硬件设备，但让 SigSession 的"可分离"部分按 TabContext 独立管理。

```
┌─────────────────────────────────────────────────┐
│  SigSession (单实例)                              │
│  ├── _device_agent      ← 绑定硬件，全局唯一     │
│  ├── _is_working        ← 采集状态，全局唯一     │
│  ├── _callback          ← 指向 MainWindow        │
│  │                                                │
│  ├── TabContext[0] 的独立数据:                     │
│  │   ├── SessionDocument (数据快照)               │
│  │   ├── SignalConfig (信号配置)                  │
│  │   ├── DecoderStack (解码器)                    │
│  │   └── DockState (Dock 状态)                    │
│  │                                                │
│  ├── TabContext[1] 的独立数据:                     │
│  │   ├── SessionDocument                          │
│  │   ├── SignalConfig                             │
│  │   └── ...                                     │
│  └── ...                                         │
└─────────────────────────────────────────────────┘
```

**这其实就是上次讨论的"方案 B"**——把信号管理、解码器、频谱等从 SigSession 下沉到 SessionDocument。本质上不是真正的多 Session，而是让 SigSession 的数据层按标签页隔离。

#### 层次 B：应用层多 Session（不改 libsigrok，但允许多 SigSession 实例）

**思路**：允许多个 SigSession 实例共存，但同一时刻只有一个能控制硬件。其他 Session 处于"离线"状态，只能查看历史数据。

```
┌──────────────────────────────────────────────────────────┐
│  SigSession[0] (活跃 — 控制硬件)                          │
│  ├── _device_agent → 全局活跃设备                         │
│  ├── _is_working = true                                  │
│  ├── _signals (实时信号)                                  │
│  └── data_feed_in() ← 接收采集数据                       │
│                                                          │
│  SigSession[1] (离线 — 查看历史)                          │
│  ├── _device_agent → 无设备绑定                           │
│  ├── _is_working = false                                 │
│  ├── _signals (从 SessionDocument 恢复的信号)             │
│  └── 无数据回调                                          │
│                                                          │
│  SigSession[2] (离线 — 查看历史)                          │
│  └── ...                                                 │
└──────────────────────────────────────────────────────────┘
```

**核心问题**：
1. **`static SigSession *_session`**：全局静态指针只能指向一个实例，`data_feed_callback` 静态方法只能桥接到一个实例
2. **`DeviceAgent`**：操作全局唯一活跃设备，离线 Session 的 DeviceAgent 无法工作
3. **32 个类的构造函数**：都接收 `SigSession*`，切换 Tab 时需要重新绑定

#### 层次 C：真正的多 Session（改 libsigrok，支持多设备同时采集）

**思路**：libsigrok4DSL 支持多个 `sr_session` 同时运行，每个绑定不同设备，可以同时采集。

```
┌──────────────────────────────────────────────────────────┐
│  libsigrok4DSL (改造后)                                   │
│  ├── sr_session[0] → Device A (DSLogic)                  │
│  ├── sr_session[1] → Device B (DSLogic)                  │
│  └── sr_session[2] → Demo Device                         │
│                                                          │
│  SigSession[0] ←→ sr_session[0]                          │
│  SigSession[1] ←→ sr_session[1]                          │
│  SigSession[2] ←→ sr_session[2]                          │
└──────────────────────────────────────────────────────────┘
```

**这是最彻底的方案，但改动量最大**。

### 四、各层次的可行性评估

#### 层次 A：伪多 Session ✅ 可行，推荐

| 维度 | 评估 |
|------|------|
| libsigrok 改动 | 无 |
| SigSession 改动 | 中等 — 将信号/解码/频谱管理下沉到 SessionDocument |
| UI 组件改动 | 小 — Dock/Dialog 通过 `bind_context` 已经能切换 |
| 风险 | 低 — 不改变采集流程，只改变数据管理方式 |
| 效果 | 同模式标签页完全独立，跨模式需限制 |

**核心改动**：

1. **`SessionDocument` 增加信号配置管理**：
```cpp
struct SignalConfig {
    int work_mode;
    int operation_mode;
    int channel_mode;
    std::vector<ChannelConfig> channels;
};
// SessionDocument 新增:
SignalConfig _signal_config;
std::vector<view::Signal*> _own_signals;  // 独立信号列表
```

2. **`View` 从自己的 Document 重建信号**，而非从全局 `SigSession::_signals` 克隆

3. **`TabContext::activate()` 时恢复硬件配置**（如果非采集状态）

4. **`DecoderStack` / `SpectrumStack` / `MathStack` 绑定到 `SessionDocument`** 而非 `SigSession`

**改动量估算**：约 15-20 个文件，2000-3000 行代码变更

---

#### 层次 B：应用层多 Session ⚠️ 可行但代价大，不推荐

| 维度 | 评估 |
|------|------|
| libsigrok 改动 | 无 |
| SigSession 改动 | 大 — 需要解决静态指针、DeviceAgent 共享、回调路由等问题 |
| UI 组件改动 | 大 — 32 个类需要支持动态切换 SigSession 指针 |
| 风险 | 高 — 多实例生命周期管理复杂 |
| 效果 | 与层次 A 相同（因为硬件仍然只能一个在采集） |

**核心障碍**：

1. **`static SigSession *_session`**：需要改为回调路由机制，让 `data_feed_callback` 能找到正确的 SigSession 实例

```cpp
// 当前：
static SigSession *_session;  // 全局唯一
```

**不可行的核心原因**：

1. **libsigrok4DSL 的全局单 session 设计**：

```c
// session.c:36

// 注释: "There can only be one session at a time."

        sr_session_destroy(); // Destroy the old.
    }
    // ...
}
```

要支持多 session，需要将 `static struct sr_session *session` 改为 `std::list<struct sr_session *> sessions`，并修改所有引用全局 session 的代码。

2. **全局单活跃设备**：

```c
// lib_main.c:61
struct sr_dev_inst *actived_device_instance;
```

所有 `ds_get_actived_device_config()`、`ds_set_actived_device_config()` 等 API 都操作这个全局变量。要支持多设备，需要将所有 API 改为接收设备句柄参数。

3. **采集互斥**：

```c
// lib_main.c:728
if (ds_is_collecting()) {
    sr_err("Error,it's collecting!");
    return SR_ERR_CALL_STATUS;
}
```

采集期间不能做任何其他操作。要支持多设备同时采集，需要每个设备有独立的采集线程和状态。

4. **USB 通信模型**：当前 USB 通信是同步的，一个设备占用 USB 连接期间不能同时操作另一个设备（即使是不同 USB 设备，驱动层也需要并发安全改造）。

5. **驱动层改造**：所有硬件驱动（DSLogic、DSScope 等）的 `dev_acquisition_start`、`dev_open`、`dev_close` 等回调都需要改为可重入的。

## 问题分析：为什么新标签页会有旧标签页的数据

### 根本原因

**`View` 是共享的，但 `_document` 和 `_data_source` 没有正确清理！**

在 `TabContext::activate()` 中：

```cpp
// tabcontext.cpp:99-103
} else {
    dsv_info("TabContext::activate() no data, setting data source to session");
    _view->set_data_source(_session);  // ← 问题在这里！
    _view->set_signal_data_from_source(_session);
}
```

当新标签页没有数据时，调用 `_view->set_data_source(_session)`，这会：

1. **设置 `_data_source = _session`**（即 SigSession）
2. **调用 `rebuild_signals()`**

而 `rebuild_signals()` 的逻辑是：

```cpp
// view.cpp:1892-1914
if (!_data_source)
    return;

auto &shared_sigs = _data_source->get_signals();  // ← 从 SigSession 获取信号
// ...
for (auto sig : shared_sigs) {
    auto cloned = sig->clone();  // ← 克隆 SigSession 的信号
    _own_signals.push_back(cloned);
}
```

**SigSession 的 `_signals` 列表包含了当前正在采集的数据！** 所以新标签页会显示旧标签页（实际上是当前 session）的数据。

### 第二个问题：`set_signal_data_from_source` 会显示 session 的数据

```cpp
_view->set_signal_data_from_source(_session);
```

这个函数会把 Signal 的 data 指针指向 `_session` 的 snapshot，也就是当前正在采集的数据。

### 正确的行为应该是

新标签页（没有数据、没有 signal_config）应该：
1. **不从 session 克隆信号**
2. **显示空的信号列表**，或者
3. **根据硬件配置重新创建信号**，但不绑定任何数据

### 修复方案

需要修改 `TabContext::activate()` 中处理"无数据"情况的逻辑：

```cpp
} else {
    // 不应该从 session 获取数据
    // 应该清空信号或根据硬件配置创建新信号
    _view->clear_signals();  // 需要添加这个函数
    // 或者调用 rebuild_signals_from_config，但用默认/空配置
}
```

或者修改 `rebuild_signals()`，当 `_document` 没有数据且是新标签页时，不从 `_data_source` 克隆。

### 当前架构的根本问题

**单 SigSession + 共享 View 的设计**导致：
- SigSession 只有一个 `_signals` 列表
- 所有标签页通过 `set_data_source(_session)` 都会获取到相同的信号
- 无法实现真正的标签页数据隔离

**要实现真正的隔离，需要：**
1. 每个标签页有自己的信号列表（不依赖 SigSession 的 `_signals`）
2. 或者 SigSession 维护每个标签页独立的信号配置

这就是为什么我之前提出的 **Plan B（每个标签页独立的 SignalConfig）** 是必要的——它允许每个标签页根据保存的配置重建信号，而不是从共享的 SigSession 获取。
