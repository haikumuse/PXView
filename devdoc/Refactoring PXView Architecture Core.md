### Planner Response

这种大规模重构（将核心数据结构从裸指针 `T*` 改为智能指针 `std::shared_ptr<T>`）引起大量编译错误是非常典型的 C++ 工程现象。出现这么多报错的根本原因在于 **C++ 的强类型系统和所有权模型（Ownership Model）发生了根本性改变**。

具体来说，主要有以下几个维度的原因导致了这波“报错海啸”：

### 1. 范围 `for` 循环的类型推导失败 (`auto*` -> `auto`)
以前代码库里大量使用了如下语法：
```cpp
for (auto *m : _session->get_signal_models()) { ... }
```
当时 `get_signal_models()` 返回的是 `vector<SignalModel*>`，推导没问题。现在它返回的是 `vector<shared_ptr<SignalModel>>`，`shared_ptr` 是一个类（Class），而不是指针（Pointer）。编译器无法把 `shared_ptr` 推导为 `auto*`，因此所有使用这种写法的循环全部报错。必须改成 `auto m`。

### 2. 手动内存管理 (`delete`) 的冲突
以前的架构大量依赖手动内存管理：
```cpp
delete _math_stack;
for (auto m : _signal_models) { delete m; }
```
引入 `shared_ptr` 的目的正是为了利用 RAII 机制自动释放内存。对 `shared_ptr` 对象调用 `delete` 是非法的 C++ 语法。我们必须把这些手动清理内存的代码删掉，或者替换为 `.reset()`。

### 3. 函数签名和接口的“涟漪效应” (Ripple Effect)
作为核心数据结构，`DecoderStack` 等类穿梭于 Core 层、View 层和 API 层之间。
当我们在 `SigSession` 中将它们改为智能指针后，任何调用了这些接口的函数（比如 `add_decoder`，`SessionService` 中的各种查找逻辑，`ProtocolDock` 里的 UI 逻辑）都会因为**参数类型不匹配**而报错。C++ 不会隐式地把 `shared_ptr<T>` 转换成 `T*`，所以这要求我们必须沿着调用链，把涉及到的函数签名全改一遍。

### 4. 强制类型转换 (`reinterpret_cast`) 失效
在 `SessionService` 这样的 API 层，旧代码为了生成唯一 ID，直接强转了指针地址：
```cpp
reinterpret_cast<intptr_t>(decoder_stack)
```
裸指针强转是允许的，但 `shared_ptr` 是一个包含控制块和指针的复合对象，不能被 `reinterpret_cast`。必须显式调用 `.get()` 获取内部的裸指针后才能强转。这导致了大量隐藏在 API 层的编译错误。

### 5. 容器与初始化列表推导失败
比如刚才遇到的 `selected.push_back({stacks[i], 4});` 报错：
以前 `stacks[i]` 是一个原生指针，编译器能很容易把它推导为一个 `std::pair<DecoderStack*, int>`。但变成 `shared_ptr` 后，C++11/14 的大括号初始化列表推导会变得非常严格，容易和内部库（比如刚才看到的 `nlohmann::json`）产生歧义，必须显式地用 `std::make_pair` 来构建。

---

**总结来说：**
这并不代表我们改错了，相反，这正是 C++ 编译器在帮我们**严格实施新的所有权边界**。裸指针允许随意传递、销毁和比较，非常灵活但也极其脆弱（这也是导致之前 Tab 切换崩溃的原因）。一旦将其收紧为 `shared_ptr`，所有过去那些“不够严谨的指针传递”、“容易导致悬垂指针的手动 delete” 都会被编译器无情地暴露出来。

最开始（在之前的对话中），我们重点讨论并着手解决的是 **PXView 架构中的一个“错位”和崩溃问题（悬垂指针问题）**。

当时你提供了一份架构分析文档，指出了在多 Tab 切换、或者清除 Session 数据时，程序很容易发生崩溃或者界面数据显示错位。

经过分析，我们得出结论，这个问题的**根本原因**在于：
1. **老旧的内存管理**：Core 层使用裸指针（Raw Pointers，如 `DecoderStack*`, `SignalModel*`）来存储数据模型，并且在 Session 刷新或 Tab 关闭时，通过手动的 `delete` 来销毁它们。
2. **生命周期脱节**：View 层（UI界面，比如 `DecodeTrace` 或各种 Dock）也保留了这些裸指针。当 Core 层销毁了对象后，View 层并不知道，其手中的指针就变成了“悬垂指针”。再一刷新界面，访问无效内存，程序就直接崩溃了。

为了**彻底且优雅地**解决这个问题，我们制定了两个阶段的重构计划：

### 阶段 1：使用智能指针（`std::shared_ptr`）替换裸指针 (✅ **刚刚已圆满完成！**)
我们将 `SignalModel`、`DecoderStack`、`SpectrumStack` 和 `MathStack` 的所有权全部升级为了 `std::shared_ptr`。
这样一来：
- Core 层和 View 层可以共享数据的所有权。
- 即使 Tab 被切换或者 Session 被重置，只要 UI 组件（View）还在引用这个 Decoder 数据，底层对象就不会被销毁。
- **这从根本上杜绝了因为生命周期不同步而导致的“错位”和内存崩溃问题。** （这也是为什么刚才我们花了这么多精力在解决数以百计的类型推导编译错误，这是为了让整个架构严丝合缝）。

### 阶段 2：引入响应式绑定（Reactive Binding） (⏳ **待进行**)
之前 UI 界面的刷新是非常笨重和脆弱的——随便改一个颜色的属性，都需要发一个全局的广播 `DSV_MSG_*`，然后整个界面跑一遍 `signals_changed()` 把所有的 UI 控件拆掉重建。
我们计划在模型（Model）内部加入 Qt 的信号（Signals，如 `appearance_changed`）。一旦核心数据改变，对应的 UI 组件直接监听并局部重绘自身，大大提升性能和架构的整洁度。

1. **核心模型事件支持 (`SignalModel`)**：
   - 继承自 `QObject` 的 `SignalModel` 新增了 `appearance_changed()` 和 `visibility_changed()` 信号。
